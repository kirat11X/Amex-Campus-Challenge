## ROLE & SCOPE

You are extending the EXISTING ProfitLens codebase. Task: add a **local, custom RAG (retrieval-augmented generation) layer** with two corpora — (A) a built-in **core corpus** derived from the project's own files (the python scoring file, the dataset, the formula's scored output, feature dictionary, framework write-up, context file, challenge PDF), and (B) a **user corpus** fed through a new frontend tab where users upload their own files for digestion. RAG is exposed to Gemini as **one more tool in the existing function-calling loop** — do NOT build a separate RAG chain, separate chat, or second model client. Do not modify W, scoring logic, existing tools' behavior, or the context-file integration.

## ARCHITECTURE (fixed)

```
User question ──► existing Gemini chat loop (system_instruction = context file)
                        │ Gemini decides per question:
                        ├── pandas tools  → exact numbers (customers, aggregates)   [unchanged]
                        ├── search_knowledge_base(query, corpus) → RAG chunks + citations   [NEW]
                        └── plain answer from Section 8 / conversation
Trust hierarchy (extend the existing one):
  live pandas tool result  >  Section 8 stats  >  RAG retrieved chunk (must cite source)  >  refuse.
For USER-UPLOADED files, RAG chunks ARE the primary source (cite filename + location).
```

- **Embeddings:** Gemini embeddings via the SAME google-genai SDK and SAME `GEMINI_API_KEY` (model name from `.env` as `GEMINI_EMBED_MODEL`, default `text-embedding-004`; verify the current free-tier embedding model name in the google-genai docs). Task types: `RETRIEVAL_DOCUMENT` for indexing, `RETRIEVAL_QUERY` for queries.
- **Vector store:** `faiss-cpu`, cosine similarity (`IndexFlatIP` on L2-normalized vectors). No external DBs, no servers, no LangChain/LlamaIndex — hand-rolled chunker + FAISS + a JSONL metadata sidecar.
- **New files:** `rag/chunker.py`, `rag/ingest.py`, `rag/store.py` (FAISS wrapper: add/search/delete-by-file/save/load), `rag/profile_docs.py` (dataset→text docs, below), and `rag_store/` (gitignored) holding `core.index`, `core_meta.jsonl`, `user.index`, `user_meta.jsonl`, and `hashes.json`.

## CORE CORPUS — WHAT TO INGEST AND HOW

Critical design rule: **never naively chunk the 500K-row CSV or the 500K-row Predictions sheet into the vector store.** Row-level numeric lookup already belongs to the pandas tools. Instead, the data and the formula's output enter RAG as **generated profile documents** — compact, retrieval-friendly text artifacts computed from them:

1. **`trial.py`** → code-aware chunks: split on top-level sections (imports/config, W dict, scoring block, equation-string builder, submission writer, FRAMEWORK dict — each FRAMEWORK entry becomes its own chunk). Metadata: `{source: "trial.py", kind: "code", lines: "40-55", section: "scoring"}`. Include the module docstring as its own chunk.
2. **`6a3eb1af6b994_feature_description.csv`** → one chunk per feature: "f13 — Lounge Access Count. Role in formula: benefit cost at $55/visit… Missing%: 2.7. Used: yes." (merge description + interpretation + usage flag).
3. **Dataset profile docs** (generated by `rag/profile_docs.py` from the CSV): one text card per feature f1–f23 containing mean/median/p5/p25/p75/p95/max, missing %, and top-20% vs rest means; plus one card for `S_all` and one overview card (500K rows, schema, missing-value semantics).
4. **Formula-output profile docs** (generated from the scored parquet / `submission_FINAL.xlsx` Predictions): one card per P&L term (definition, coefficient, mean top-20% vs rest, share of total separation), a profit-distribution card (all percentiles, cutoff $2,012.86, 45.2% negative), a segment-economics card, and an integrity card ("Predictions sheet = profit rounded to 4dp; verified match 500,000/500,000").
5. **`submission_FINAL.xlsx` → "Profitability Framework" sheet**: each section row (Variables Used, Equation, Prediction Logic, Coefficient Derivation, Validation Approach, …) = one chunk, metadata `{source: "submission_FINAL.xlsx", sheet: "Profitability Framework", section: <name>}`.
6. **`PROFITLENS_CONTEXT.md`** → chunk by `##`/`###` headers (a header + its body = one chunk; split bodies >1,200 chars at paragraph boundaries with the header repeated).
7. **`6a3ea743b1106_campus_challenge26_r1.pdf`** (if present) → extract text per slide/page (pypdf), one chunk per page, metadata includes page number.

Chunking defaults everywhere else: ~800 chars target, 120 overlap, never split mid-sentence/mid-line-of-code. Every chunk stores: `chunk_id (sha1 of content)`, `source`, `kind (code|data_profile|framework|context|slide|user)`, `location` (lines/section/page/sheet), `text`.

**Core index build:** `rag/ingest.py build-core` runs at app startup only if `hashes.json` shows any source file changed (compare file sha256); otherwise load the saved index. Print chunk count at startup (expect roughly 80–150 core chunks).

## NEW TOOL — `search_knowledge_base`

Add to `tools.py` alongside the existing tools, with a Gemini function declaration:

```
search_knowledge_base(query: str, corpus: "core" | "user" | "both" = "both", k: int = 5)
```

- Embed query (`RETRIEVAL_QUERY`), search the requested FAISS index(es), return top-k as
  `{"results": [{"source", "location", "kind", "score", "text"}], "note": ...}`.
- If the user corpus is empty and corpus includes "user", add `note: "no user files ingested yet"`.
- Similarity floor 0.5 (after normalization) — below it return `{"results": [], "note": "nothing relevant found"}` so the model says it couldn't find support instead of hallucinating.
- Update the tool-usage guidance appended to the system instruction (keep it ≤10 lines, added to the runtime block — do NOT edit PROFITLENS_CONTEXT.md itself):
  "Use search_knowledge_base for: questions about the code/implementation, the methodology write-up, the challenge rules/deck, feature meanings, and ANY question about user-uploaded files. Do not use it for customer-level numbers or live aggregates — those come from the pandas tools. When you answer from retrieved chunks, cite the source and location (e.g., 'per trial.py lines 40–55' or 'from your uploaded report.pdf, p.3'). If retrieval returns nothing relevant, say so."

## FRONTEND — NEW TAB: "📂 Digest your own files?"

Restructure `app.py` with `st.tabs(["💬 Chat", "📂 Digest your own files?"])`. Chat tab = current UI unchanged.

Digest tab requirements:
1. Header: **"Do you want to digest your own files?"** with a one-line explainer: "Upload documents and ProfitLens will read them and answer questions about them alongside the built-in analysis."
2. `st.file_uploader` (multi-file) accepting: `.pdf, .docx, .txt, .md, .csv, .xlsx, .py, .json`. Per-type parsing: pdf→pypdf per page; docx→python-docx paragraphs; csv/xlsx→**profile-doc treatment** (schema + dtypes + per-column stats + first 20 rows as a markdown table — never full-row chunking; if >50K rows, stats only) plus each sheet handled separately for xlsx; py→code-aware chunks; txt/md/json→header/paragraph chunks. Reject files >25 MB or unparseable ones with a friendly toast, never a crash.
3. On upload: spinner "Digesting <name>…", chunk → embed (batched) → add to `user.index` + `user_meta.jsonl`, then success toast "✓ <name> digested — <n> chunks".
4. Ingested-files panel: table of filename, type, chunks, ingested-at; per-file 🗑 delete (removes its vectors via delete-by-file rebuild of the small user index) and a "Clear all my files" button with confirm.
5. Sidebar toggle (visible on both tabs): **"Include my uploaded files in answers"** (default ON when user corpus non-empty). When OFF, `search_knowledge_base` forces `corpus="core"` regardless of what the model requested.
6. Persistence: user index survives app restarts (loaded from `rag_store/`); show count on boot.
7. Duplicate guard: same content hash re-uploaded → "already digested", no re-embedding.

## EMBEDDINGS — FREE-TIER HARDENING

- Batch embed up to 100 chunks per request where the SDK supports it; otherwise sequential with 429 exponential backoff (2s/4s/8s, reuse the existing retry helper).
- Content-hash embedding cache (`rag_store/emb_cache.sqlite` or a pickle dict keyed by sha1) so re-ingestion and index rebuilds never re-pay embedding calls.
- All embedding vectors L2-normalized before insertion.
